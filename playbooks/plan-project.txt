# /llm_harness/playbooks/plan-project.txt
# use when: a new project, a big redesign, or a request that forces several consequential decisions about architecture, interfaces, data ownership or behavior across systems
Plan the project before any code. The result is one living file, docs/plan.md, plus a Todo note for the first milestone only.
Frame first: say in one line the outcome the owner wants, apart from the solution and examples the request names. If another framing would change the architecture, avoid large rework or fit the pinned goal better (reuse an existing tool or project, and ask the owner to have it looked up when you cannot check; a host platform or adapter instead of building the thing in; another place in the architecture), put it at the top of the interview message with your recommendation, and plan only the framing the owner picks.
1. Interview. First sort what the owner already wrote into asked for, decided and only suggested, so you never ask about a decision already made. Then ask at most 7 questions in one message, each with your recommended answer: who uses it, what it must do first, platforms, data and where it lives, scale, integrations, constraints, and what is out of scope.
2. Vision. Write it in the owner's words: one paragraph, a list of non-goals, and a one-line goal to pin with @GOAL (ask first).
3. Options. Existing project: read the tree nodes and run @XREF <name> | impact on what would change; search @KB for each technology. New project: propose 2 or 3 architectures; for each give its shape, when it fits, what it costs and its biggest risk.
4. Decide. The owner picks. Record every decision with the alternatives rejected and what would make us revisit it.
5. Milestones. 3 to 7, ordered so the riskiest unknown comes first. Each ends in something the owner can run or see and has 2 to 4 "done when" lines (outcomes, not steps). A milestone is an outcome, not a unit of work: do its related changes together, not one per prompt.
6. Write docs/plan.md as a decision record, not a specification: Vision and boundaries, Decisions with their rejected alternatives, Milestones with their dependencies, Progress (what changed, known gaps), Open questions. Never every requirement or implementation step; those belong in the Todo notes. Propose the tree nodes for the chosen architecture; the owner approves them before any code.
7. Hand-off. Propose Todo notes for milestone 1 only, one per chat, each carrying its "done when" lines. Add and pin them only when the owner approves. Later milestones stay in docs/plan.md until reached.
8. While building: update docs/plan.md after each milestone (what was done, gaps with workarounds, decisions that changed), not every turn. A change that contradicts a decision means stop and ask.
